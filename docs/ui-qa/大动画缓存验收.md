# 大动画缓存与旧256 MiB报错修复（IV-ANIM-01）

## 根因与实现

v0.7.0 将 GIF/APNG/WebP/AVIF 的整段合成帧加首帧副本限制为256 MiB，并将预算错误归类为 UnsupportedFormat。压缩文件很小也可能因帧数和分辨率导致展开后超限。

新增 AnimationBuilder：小动画保留原内存路径；预计帧堆数据（含小动画首帧副本）超过64 MiB时，已解码帧及后续帧写入本进程私有临时文件。解码成功后建立只读内存映射，帧只保存共享映射与偏移。首帧Mip共享同一映射，不重复保留整帧。读取、GPU上传、取色、编辑与OCR仍使用原始RGBA字节，不缩小图像、不丢帧、不降低帧率或改帧时长。

Windows文件独占打开并使用DELETE_ON_CLOSE；Unix使用0600权限并创建后立即unlink。映射和文件句柄不对外暴露，发布映射后不再修改/截断文件；最后一个引用释放后解除映射并关闭文件。文件空间不足/权限错误明确返回，失败不交付残缺帧序列。不会写回用户源图。

安全边界：单帧像素数据最多256 MiB、最多4096帧；64位单动画展开数据最多8 GiB，本进程临时帧文件总预算16 GiB。64 MiB是堆帧数据转存阈值，不是整个进程、系统文件缓存或GPU内存上限；原生解码工作区、当前帧上传和操作系统分页另计。仍先完成整段解码再开始播放，慢盘可能影响首次打开和分页读取。静态PNG/WebP沿用原静态解码限制，缩略图仍只取首帧。

内存映射依据：memmap2 0.9.11（沿用Cargo.lock已有版本），https://docs.rs/memmap2/0.9.11/memmap2/struct.Mmap.html 。仅映射独占私有缓存，绝不映射可能被外部编辑的源图。

## 可重复验证

```powershell
python -B tools/ui-qa/generate_large_animations.py <新建测试目录>
$env:LCL_IV_LARGE_ANIMATIONS = '<测试目录>'
cargo test --workspace --locked
cargo test -p iv-core --test large_animation_cache --locked -- --ignored --nocapture
python -B -m unittest discover -s tools/tests -p 'test_*.py'
python -B tools/ui-qa/large_animation_smoke.py --binary <当前imageview.exe> --fixtures <测试目录> --output <新建截图目录> --commit <构建提交>
```

测试图：GIF/APNG/WebP各72帧、1024×1024，共288 MiB原始RGBA帧，已超过旧上限；带透明区域、不同颜色与40/50/60ms帧时长。GIF以编码后Pillow像素为基准，不把编码调色板量化当作缓存错误。WebP与libwebp/Pillow的既有合成舍入可能有1级差异，跨解码器抽样允许2级，同时对所有格式的全部帧与原image crate迭代器逐字节比较，确保缓存本身完全无损。缩略图首帧、反向读取、映射引用存活及进程退出临时文件清理也检查。
